# KICE 기출 응시 내구성 보완 — 2026-09-07

## 재현한 결함과 범위

부모 통합 작업에서 iPhone 시뮬레이터의 실제 KICE 화면으로 확인했습니다.
`-demo -kice suneung-2026`에서 1번의 3번 선지를 선택한 뒤 미응답 29문항,
경과 01:05가 표시됐습니다. 데모 데이터 삭제 없이 `-demo -preserveDemoState
-kice suneung-2026`로 다시 실행하자 미응답 30문항, 경과 00:05로 되돌아갔습니다.
기존 답안/선택과목은 AppStore 메모리, 결과/타이머는 화면 메모리에만 있었습니다.

이 변경은 내부 Debug에서 허용된 KICE 응시의 저장·복원 보완입니다. 기존 Release
리소스 제외, 저작권 안내, 원문 PDF 사용 허가 조건은 변경하지 않았습니다. 이 문서는
상용 원문 탑재 허가나 App Store 심사 통과를 뜻하지 않습니다.

## 저장 및 화면 계약

- `KiceStudyArchive.swift`: 계정 슬롯별 `kice-study-archive-v1.json` 하나에 현재 응시,
  선택과목, 과목별 답안, PDF 페이지, 누적 실제 학습 경과시간, 불변 채점 receipt를
  저장합니다. 계정/스키마/자료 fingerprint/크기/문항 수/시간 범위를 검사합니다.
- `KiceStudyRepository.swift`: 캡처한 계정 경로와 세대 handle을 사용합니다. 일반
  입력은 150ms debounce, 채점/새 응시/명시적 화면 이탈은 저장 확인 경계를 거칩니다.
  인코딩과 파일 I/O는 직렬 비동기 writer가 수행하며 보호된 원자적 교체를 사용합니다.
- 읽을 수 없는 파일은 빈 기록으로 취급하지 않습니다. 자동 덮어쓰기를 막고 오류와
  재시도/명시적 초기화 동작을 제공합니다. 초기화는 원본의 SHA256 검증 백업이
  성공한 뒤에만 교체하며, 다른 학습 기록과 오답노트는 삭제하지 않습니다.
- 화면 타이머는 파일의 누적값을 복원한 뒤 실제 화면 학습 시간만 이어 갑니다.
  화면 이탈/비활성화 동안은 일시정지합니다. 부모 작업의 가로 OMR 고정 채점 버튼과
  결과로 스크롤하는 동작은 유지했습니다.
- 채점 후에는 저장이 확인된 receipt만 결과로 표시합니다. 같은 응시를 다시 채점해도
  같은 receipt가 반환됩니다. 새 응시는 이전 효과 반영 완료와 별도 사용자 확인이
  필요합니다. 응시 ID 및 계정 세대를 캡처하여 늦은 버튼/텍스트/Task가 다음 계정이나
  다음 응시의 답안을 변경하지 못하게 했습니다.

## 통계·오답·이벤트 재시도

여러 파일 전체가 한 파일시스템 트랜잭션인 것처럼 가정하지 않습니다. 순서가 있는
receipt와 각각의 멱등 키로 중간 종료 뒤 이어갑니다.

1. 채점 결과와 오답이 적용될 대상 ID/신규 여부를 receipt에 먼저 동결하고 저장합니다.
2. 오답 스냅샷과 해당 receipt ID를 같은 오답 파일에 함께 저장합니다. 이후 receipt의
   로컬 효과 완료 단계를 저장합니다. 이 사이에 종료되어도 SRS와 wrongCount를
   중복 적용하지 않습니다. 이미 더 나중에 복습한 상태도 되돌리지 않습니다.
3. 학습 이벤트는 `kice-grading-<receipt>-<문항>` 고정 ID, 동기화 작업은 receipt
   기반 고정 ID를 사용합니다. 실제 최초 채점 일시를 재사용합니다. 기존 호출자가
   선택 인자를 보내지 않으면 기존 UUID/현재 시각 동작이 유지됩니다.
4. 이벤트 파일과 서버 계정의 로컬 전송 큐가 저장된 뒤 효과 완료를 표시합니다.
   이 표시는 **서버 반영 완료**라는 뜻이 아니라 내구성 있는 로컬 큐 적재 완료입니다.
   전송/재로그인/네트워크 실패는 기존 SyncEngine이 담당합니다.

새 KICE 누적 문항/정답 수는 고유 receipt 원장에서 한 번씩 합산합니다. 기존의
혼합 과거 통계는 원인을 추측하여 빼거나 다시 분류하지 않습니다. AppStore의 한
표시 경계에서 기존 통계와 신규 receipt 기여를 합성하고, 일반 문제의 증가분은 기존
기본 통계에만 저장합니다. 진도 초기화 시 별도 통계 epoch를 바꿔 과거 receipt의
통계가 재실행으로 살아나지 않게 했습니다. 채점 결과 자체는 유지합니다.

기존 최고점/활동일은 표시용 UserDefaults 거울값입니다. 완료 receipt를 다시 읽을 때
최고점 max/활동일 합집합으로 복구하므로 이 거울값 저장 직후 종료도 복원할 수 있습니다.
복구가 다시 채점하거나 이벤트/SRS를 재실행하지는 않습니다.

## 추가로 재현한 파일 read 경합

실제 파일을 읽는 지점의 실행 시점만 제어한 회귀에서 다음 순서를 재현했습니다.

1. 이전 답안을 파일에서 읽은 비동기 read를 반환 직전에 정지합니다.
2. 새 답안을 저장하고 ACK를 받아 pending 항목이 사라집니다.
3. 이전 read를 재개합니다. 수정 전에는 이 과거 스냅샷이 UI로 돌아와 다음 저장에서
   새 답안을 다시 덮었습니다.

현재는 최신 수락 모델 revision과 최신 실제 저장 revision을 따로 추적하고,
늦은 read에는 더 최신의 저장 완료 스냅샷을 반환합니다. 이전 revision의 저장도
거절합니다. 명시적 원본 보관 초기화는 handle epoch를 바꿔 초기화 전 read가
이전 답안을 복원하지 못하게 했습니다.

계정 경계/표시 거울값 복구의 최종 통합 빌드 및 GUI 증거는 부모 통합 작업이 별도로
기록합니다. 이 문서 작성 시 이를 완료한 것으로 주장하지 않습니다.

## v13c 시뮬레이터 복원 후 타이머 정지 후속 수정

부모의 v13c 실제 시뮬레이터에서 1번 3선지/미응답 29/08:40 입력 후 재실행하여
선택과 미응답 29, 누적 08:49 복원을 확인했습니다. 다만 이후 시간이 멈추고 실행
표시점이 사라졌습니다. 멈춤은 정책이 아니며 활성 기출 화면은 자동 재개해야 합니다.

실제 `ExamTimer`와 제품 화면의 `syncTimerAvailability` 메서드를 컴파일한 실행
회귀로 정지 가능한 순서를 재현했습니다. 파일 로드를 await하는 Task가 최초 View의
`scenePhase=.inactive`를 캡처하고, 그 사이 새 `.active` View가 시간을 재개한 뒤,
늦은 Task가 최초 View를 통해 다시 pause합니다. 그 후 변화가 없으면 08:49에
계속 머뭅니다. 이는 GUI에서 관찰한 결과를 만들 수 있는 제품 메서드 경합의 재현이며,
해당 GUI 실행의 내부 scene 이벤트 로그를 수집했다고 주장하는 것은 아닙니다.

`KiceTimerLifecycle.swift`를 추가해 화면 `@State`가 공유 lifecycle 객체를 소유하게
했습니다. 늦은 View 값도 최신 visible/active 값을 읽습니다. `.onAppear`·scene 변경·
`.onDisappear`가 이 값을 갱신하고, 취소되거나 사라진 화면의 로드 완료는 타이머를
살리지 않습니다. 기존 저장/채점/계정 gate와 채점 결과의 고정 시간은 유지합니다.

`run-kice-timer-resume.sh`는 수정 후 08:49→08:50 실제 누적 증가, 배경 정지,
전경 자동 재개, 편집 gate, 화면 이탈 후 늦은 완료 차단, 결과 시간 고정을 통과했습니다.
타이머 공통 구현이나 초당 발행 정책은 바꾸지 않았습니다. 최신 전체 SwiftUI 빌드와
GUI 자동 재개 확인은 부모 통합 작업이 이어서 수행합니다.

## 남는 경계와 비수행 항목

- 강제 종료가 150ms debounce/디스크 ACK보다 먼저 일어나면 마지막 미확정 입력까지
  보장하지는 않습니다. 경과시간은 대략 1초마다 체크포인트하며, 명시적 종료/배경 전환은
  정확한 누적값을 flush합니다. 운영체제가 실행 시간을 전혀 주지 않은 강제 종료도
  완전한 마지막 바이트 저장이라고 표현하지 않습니다.
- KICE 기출 응시 원장 자체는 계정별 **이 기기** 저장입니다. 다른 기기의 KICE 답안/
  타이머/결과 복원 API를 새로 만들거나 있다고 표시하지 않았습니다. 기존 학습 이벤트와
  오답의 서버 동기화는 별도입니다.
- 한 archive는 최대 12MiB/2,000개 receipt/100개 시험으로 제한합니다. 한도 초과는
  오류로 드러내며 기존 기록을 자동 삭제하지 않습니다.
- 실제 iPhone 설치/실기, 운영 DB, 운영 서버 재시작, TestFlight 업로드, 심사 재제출,
  커밋/브랜치/푸시는 이 하위 작업에서 하지 않았습니다.
